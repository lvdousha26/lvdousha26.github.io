02开发环境：别在选工具上卡住

写 C 之前得先有个地方能编译、能运行、能调试。这件事本身不难，但选错了会先卡掉你半天——而且是被工具坑，不是被 C 坑。

先看两个别碰的。它们不是"过时了所以不好"，是真的会让你学到错的东西：

这两个别再用了
VC 6.0（Visual C++ 6.0）：1998 年的产品。编译器只认 C89，for (int i = 0; ...) 这种写法直接编不过（C99 才允许）；跟课程评测机、竞赛环境也不是一套——你在它上面"跑通了"，换个 gcc 就是一堆错。

Dev-C++（原版 5.11）：2005 年就停止维护了，现在流传的版本调试器常和 gdb 对不上，中文路径、UTF-8 编码、报错定位都容易出毛病。看着像能用，真出问题没人修。

那用什么？按你现在要干的事选，不按"哪个更专业"选：

工具好在哪代价适合

Red Panda		 Dev-C++ 的现代重写版，自带编译器和调试器，中文界面，装完双击就能编译运行，C99 之后的语法全支持 生态小，只适合单文件作业，做不了大工程 上课写作业的首选，Dev-C++ 的正经替代
CP Editor 专为算法题做的：一键编译运行、把样例贴进去逐个自动比对、还能直接提交到洛谷 / Codeforces 只管单文件，写不了项目 刷题、打比赛
Visual Studio

  • Windows 上写课程设计：Visual Studio。慢是慢，但调试真省事
  • 想长期用一套、以后写项目：VS Code。花半小时配好，之后最舒服（配置见 13.3 节）
  • 想折腾、以后要上服务器：vim。值得学，但别在赶作业的那一周开始学

但有一件事跟工具无关：不管你用哪个，命令行那套迟早要会（第 13 节）。评测机、服务器、CI 上没有 IDE，只有 gcc 和一个黑框。IDE 是让你写作业舒服，命令行是让你在别人的机器上也能干活。

别在选工具上卡三天
工具三个月就能换一套，代码和思路才是攒下来的。先用能跑起来的那个，遇到真正的瓶颈再换。很多人的问题是"一直在选编辑器"，而不是"编辑器不好用"。

补一句：vim 的改版、发行版，还有几个平替

上面表里 vim 只占一行，其实它的生态比"一个编辑器"大得多。真要往这条路上走，这几个词迟早会撞见：

  • Neovim：vim 的分支，现在社区的主力。异步执行（跑补全、跑格式化不卡界面）、配置用 Lua、内置 LSP。你在网上看到的"vim 配置"，八成说的是它
  • gVim：vim 的图形界面版，鼠标能点，其余操作一样。Windows 上想试又不想全键盘，可以先从它开始
  • 发行版（配好的一整套）：LazyVim / LunarVim / NvChad / AstroNvim。主题、补全、文件树、LSP 全替你配齐，装完直接写代码——比自己从零写配置省几个月
  • 插件生态：vim 难配就难在什么都要自己挑。常见的几类：文件跳转（Telescope / fzf-lua）、文件树（nvim-tree / oil）、语法高亮（Treesitter）、补全与诊断（LSP + cmp / blink）、状态栏（lualine）、Git 标记（gitsigns），插件管理器用 lazy.nvim
  • 成本要提前知道：从零配一套顺手的 Neovim，头一个月基本在改配置而不是写代码。这不算坏事，但要挑空的时候做，别赶作业那一周

而且不是所有人都需要模态编辑。只想"在终端里改个文件"的话，下面这几个更省事：

工具特点什么时候用
nano 几乎所有 Linux 都预装，屏幕底部直接列着快捷键：^O 保存、^X 退出（^ 就是 Ctrl）。零学习成本 连服务器改配置、临时救急。不会 vim 也能立刻上手

03教材篇：别买谭浩强，别买地摊书

关于谭浩强

  • 初版是 1991 年，代码风格陈旧，大量使用 gets() 这类已被 C11 标准移除的危险函数
  • 示例重应试、轻工程，很多写法在现代 C 里是不推荐的
  • 部分概念表述不准确（比如早期版本的 void main()）

关于地摊书

凡是标题带"21 天精通""从入门到放弃""一本就够"的，一律别买。这类书多数是拼凑出来的，代码错误多，还会把坏习惯教给你。

入门先读这个：阮一峰的《C 语言教程》

免费、在线、不废话，一个周末能读完：wangdoc.com/clang/intro。

  • 快：没有长篇铺垫，概念讲完就给例子，适合先把"C 大概长什么样"建立起来
  • 现代：全篇用 GCC 命令行举例，-std=c99、a.out、-o 这些一开始就讲清楚，跟你上机用的是同一套东西
  • 不绕：不堆术语，读到不懂的地方可以直接往下走，不会卡死

但它偏"语法与要点"，讲到够用就停：指针只到能看懂的程度，内存布局、链接这些底层不展开。所以它是入门的第一本，不是唯一一本。

05核心难点：指针怎么理解

5.1 先建立内存模型

把内存想象成一排酒店房间：

内存示意
地址          内容
0x1000      [  42  ]      <- 变量 a，int a = 42;
0x1004      [ 0x1000 ]    <- 变量 p，int *p = &a;

三句话记住：

  1. 变量名只是给你看的，CPU 只认地址
  2. 每个变量都住在某个地址上
  3. 指针就是"房间号"本身，它自己也有房间

5.2 两个运算符

  • &x：取地址（拿到房间号）
  • *p：解引用（顺着房间号走进去，操作里面的东西）
  • * 和 & 互为反操作
最容易被绕晕的一点
声明里的 int *p，那个 * 不是解引用，只是标记"p 是个指针"。声明看类型，表达式才看运算。

类型很重要：int * 解引用时读 4 个字节，char * 读 1 个字节；指针加 1 不是地址加 1，而是加上"一个元素的大小"。

5.3 进终端看：指针在指令层面做了什么

上面那个演示是"内存视角"。但 CPU 真正执行时，指针操作会被拆成两条指令，中间必须经过寄存器。寄存器是 CPU 内部的一小块超快存储，只有十几个格子；一条指令也不能直接把一个内存地址的内容搬到另一个内存地址——必须"内存 → 寄存器 → 内存"绕一圈。这就是指针操作看起来很绕的根本原因。

下面这个迷你终端是教学模拟（不是真 shell）：输入 C 语句，它一步步执行，把 寄存器和内存格子的变化实时画在右边。先敲这几条试试：

c-sim · 教学用迷你终端（模拟，不是真 shell）
$
寄存器
内存

回车执行，↑ / ↓ 翻历史命令，右上角可以重置。试试按顺序敲这五条：

建议的操作顺序
int a = 42;      // 常量直接写进 a 的内存
int *p = &a;     // 取 a 的地址，存进 p
*p = 100;        // 顺着 p 里的地址写 → 改的是 a
p a              // 42 变成了 100
int *q = NULL;   // 空指针，试试 *q = 1; 会怎样

跑完会发现三件事，正好是理解指针的关键：

  1. &a 不读 a 的值，只算地址。对应的指令是 leaq（load effective address）——它只做地址计算，根本不访问那块内存。这类 C 与汇编的对应关系，13.4 节末尾有完整对照表
  2. 指针变量自己也有地址、也占内存。64 位系统里 int * 占 8 字节，int 占 4 字节，所以 a 在 0x1000，p 在 0x1008
  3. *p = 100 是两条指令：先 movq p(%rip), %rax 把地址读进寄存器，再 movl $100, (%rax) 往这个地址写。p 从头到尾没变，变的是 a
这就是"指针为什么难"的答案
你写 *p 是一个符号，CPU 执行的是"读地址 → 再访存"两次操作。中间那个寄存器（rax）就是"临时拎着的门牌号"。理解了这个模型，int **pp、指针数组、链表节点里的 next 都只是这个动作套娃。

5.4 完整示例

C
#include <stdio.h>

int main(void) {
    int a = 42;
    int *p = &a;              // p 存放 a 的地址

    printf("a 的值   = %d\n", a);       // 42
    printf("a 的地址 = %p\n", &a);      // 0x7ffd...
    printf("p 的值   = %p\n", p);       // 和 &a 相同
    printf("p 指向的 = %d\n", *p);      // 42

    *p = 100;                 // 通过指针改 a
    printf("a 现在   = %d\n", a);       // 100

    return 0;
}

5.5 指针和数组

C
int arr[5] = {1, 2, 3, 4, 5};
int *p = arr;        // 数组名退化为首元素地址

p[2]     == arr[2];  // true
*(p + 2) == arr[2];  // true，指针加 2 实际跳过 2 个 int

两个高频坑：

C
printf("%zu\n", sizeof(arr));  // 20（5 * 4），整个数组
printf("%zu\n", sizeof(p));    // 8，指针自身大小（64 位系统）

void f(int arr[]) {
    printf("%zu\n", sizeof(arr));  // 8，数组传参后退化成指针
}
面试常考点
数组一旦传进函数，就退化成指针，函数内部拿不到数组长度。所以数组传参时要额外传一个长度参数。

5.6 为什么需要指针：函数参数

C 语言是值传递：函数收到的只是拷贝，改不了外面的变量。

C
void bad_swap(int x, int y) {       // 无效！改的是副本
    int t = x; x = y; y = t;
}

void good_swap(int *x, int *y) {    // 有效
    int t = *x; *x = *y; *y = t;
}

int main(void) {
    int a = 1, b = 2;
    good_swap(&a, &b);
    printf("%d %d\n", a, b);        // 2 1
    return 0;
}

指针存在的三大理由：

  1. 让函数能修改调用者的数据
  2. 避免大结构体的拷贝，提高效率
  3. 表达"可能为空、可能没有"的语义（NULL）

5.7 指针的常见坑（考前必背）

  1. 野指针：int *p; *p = 10; 指针没初始化，指向随机地址，直接崩溃
  2. 空指针解引用：int *p = NULL; *p = 10; 崩溃
  3. 悬空指针：函数返回局部变量的地址，函数结束后栈内存失效
  4. 数组越界：长度为 10 的数组访问 arr[10]，不一定立刻崩溃，但会写坏相邻内存，这种"没崩的"最危险
  5. 修改字符串字面量：char *s = "hello"; s[0] = 'H'; 未定义行为
  6. sizeof 与 strlen 混淆：前者包含 \0，后者不包含
  7. malloc 与 free 不配对：进阶内容，先记住"要配对"

5.8 练习方法

每写一个指针程序，在纸上画三列：变量名、地址、内容，用箭头画出指向关系。画一个月，指针就通了。指针这关至少留两周专门啃，别跳。二级指针先不用深究，见到不慌就行。

5.9 未定义行为（UB）：编译器没义务按你想的来

上面反复出现"未定义行为"这个词。它不是"会报错"——恰恰相反，它连错都不报。

C 标准对一些写法不规定任何行为，只写一句 "undefined behavior"，意思是编译器可以做任何事：照你想的跑、算出个垃圾值、把整段代码删掉、或者让程序在完全无关的地方崩掉。它描述的不是"某种错误结果"，而是"这里没有规则"。

写法为什么是 UB你可能看到的现象
arr[10]（长度 10）那块内存不归你多半没事，换个优化等级或编译器就崩
int *p; *p = 1;野指针段错误，或者悄悄写坏别的变量
free(p); *p = 1;释放后使用内存被别人复用后才崩，最难查
int x; if (x == 0)读未初始化变量有时是 0，有时是垃圾值
x + 1（x 为 INT_MAX）有符号整数溢出编译器可假定不会发生，直接删掉你的判断
a / 0（整数）除零直接崩；浮点除零得到的是 inf
char *s = "hi"; s[0] = 'H';字面量在只读段段错误
i = i++ + 1;同一句里改了两次结果随编译器、随优化等级变
三个经典 UB，看起来都很正常
// 1. 你以为它在检查溢出，其实 -O2 下整个 if 会消失
int add_one(int x) {
    if (x + 1 < x) {            // 有符号溢出是 UB：编译器直接假定不会发生
        printf("overflow!\n");
    }
    return x + 1;
}

// 2. 未初始化的变量，值不是"随机的"，是"什么都可能"
int x;
if (x == 0) puts("zero");    // 进不进得去，天知道

// 3. 同一句里改两次同一个变量
int i = 0;
i = i++ + 1;                 // 不同编译器给出 0 或 1，甚至不同优化等级都不一样
为什么它在 -O0 下看起来好好的
-O0 基本按你写的顺序逐条翻译，越界写在栈上常常"刚好"落在没用的地方，于是侥幸跑对。一旦打开 -O2，编译器就开始利用"UB 不会发生"这个假设做变换——不是它变坏了，是它开始兑现你从没兑现过的承诺。所以"我这儿跑得好好的"从来不是证据。

怎么防，从便宜到贵：

  1. 编译开 -Wall -Wextra：未初始化、隐式声明、可疑比较，它能替你挡掉一批
  2. 用 sanitizer 跑一遍：gcc -g -fsanitize=address,undefined main.c -o main。ASan 抓越界和 use-after-free，UBSan 抓有符号溢出、非法移位、空指针解引用——慢 2~5 倍，但报错精确到行号，比 gdb 事后猜强得多
  3. Linux 上再上 valgrind：valgrind ./main，不用重新编译
  4. 根本上还是别写：变量一定初始化、指针先判空、循环写 i < n 而不是 i <= n、free 之后把指针置 NULL
一句话记住
能跑不代表对。C 语言把"你保证过的事"当成真的：你写了越界，它就有权假设你不会越界。面试里问 i++ + i++、问"这段代码为什么要这么写"，考的就是这件事。

07代码可读性：写给三个月后的自己

先把一件事说清楚：可读性不是"好看"，是维护成本。你写的代码有两个读者——编译器只关心语法对不对，三个月后的你才决定它还改不改得动。课程作业几十行，怎么写都能跑；但到了几百行、几千行，难读的代码会让你连自己的 bug 都找不着。

这一段讲四件事：名字怎么起、缩进怎么缩、注释写什么、函数怎么切。全是立刻能用上的，不需要任何新知识。

7.1 命名：让名字自己解释

一条判断标准就够：把这个名字读出来，能不能知道它是什么、用来干什么。读完还得猜的，就该改。

别这么写改成为什么
int a, b;int studentCount, passedCount;类型不是身份，a、b 没有信息量
int flag;int isSorted;flag 只说"有个标记"，没说标记什么
void f(int x);int maxOf(int a, int b);函数名要说"做什么"，动词开头
int temp;int prevValue;temp 只说"临时"，没说临时存什么
int n;（跨二十行）int nodeCount;作用域越大，名字要越具体

几条可以直接照做的规则：

  • 布尔量用 is / has / can 开头：isEmpty、hasCycle、canMove。这样 if (isEmpty) 读起来就是一句人话
  • 常量全大写：MAX_SIZE、INF，跟普通变量一眼区分开
  • 指针名字带上"指向什么"：p 用在三行的循环里没毛病，但 head、current、prevNode 比 p1 p2 p3 强太多
  • 名字长度看作用域：循环下标 i、j 是惯例，可以短；跨函数、跨几十行的变量必须写全
刷题时的例外
算法题里 n、m、i、j 是公认缩写，题解和教科书都这么写，这时候不必强行改成 count。但只要代码是"要给别人看、要被别人改"的（课程设计、项目、实习），标准立刻变严。这是分场景，不是双重标准。

7.2 缩进与格式：让结构一眼可见

缩进不是为了好看，是为了把"谁属于谁"画出来。读代码时眼睛先扫缩进轮廓，再往里看内容。

  • 统一 4 个空格（或统一 2 个），一个文件里不许混用
  • 绝不 tab 和空格混用。这就是"我这儿好好的、你那儿全乱"的元凶，也是 git diff 里一堆假改动的来源。VS Code 里把 editor.insertSpaces 设成 true、editor.tabSize 设成 4，按 Tab 自动变成四个空格
  • 左大括号不换行（K&R 风格），项目内统一就行，不用纠结哪种更"正确"
  • 一行只做一件事：if (a) b(); 这种压缩写法，调试时连断点都不好下
  • 用空行分组：变量声明一段、核心逻辑一段、return 前空一行

同一段冒泡排序，两种写法，逻辑一模一样：

难读（能跑，但没人想改）
int main(){int a[100],n,i,j,t;scanf("%d",&n);
for(i=0;i<n;i++)scanf("%d",&a[i]);
for(i=0;i<n;i++)for(j=0;j<n-i-1;j++)if(a[j]>a[j+1]){t=a[j];a[j]=a[j+1];a[j+1]=t;}
for(i=0;i<n;i++)printf("%d ",a[i]);return 0;}
好读（同样的逻辑）
#include <stdio.h>

#define MAX_N 100

int main(void) {
    int values[MAX_N];
    int n;

    scanf("%d", &n);
    for (int i = 0; i < n; i++) {
        scanf("%d", &values[i]);
    }

    // 冒泡：每轮把最大的送到末尾
    for (int i = 0; i < n - 1; i++) {
        for (int j = 0; j < n - 1 - i; j++) {
            if (values[j] > values[j + 1]) {
                int tmp = values[j];
                values[j] = values[j + 1];
                values[j + 1] = tmp;
            }
        }
    }

    for (int i = 0; i < n; i++) {
        printf("%d ", values[i]);
    }
    return 0;
}

差别只在缩进、空格、命名和空行。但第二种你能一眼看出"外层在轮次、内层在比较、三个变量在交换"——这才是缩进真正省下的时间。

7.3 注释：解释"为什么"，不是"是什么"

代码本身已经说了"在做什么"，注释再复述一遍就是噪音。值钱的注释全是"为什么"：为什么这里要 +1、为什么这个看着多余的分支不能删、这个魔数是从哪个公式来的。

三种注释对比
// 废话：只是把代码翻译成中文
i++;

// 有用：解释了意图，别人就不敢乱删
i++;  // 跳过行尾的 '\n'，否则读下一个字段会多出一个空串

// 有用：解释了魔数的来源
// 采样率 44100 来自课程给定的音频格式，不要改
int samplesPerSecond = 44100;
  • 函数头写清四件事：做什么、参数含义、返回什么、特殊情况（比如传 NULL 会怎样）
  • 别用注释屏蔽死代码：不要了就删，git 里有历史。留一堆注释掉的代码，只会让后面的人不敢动
  • 改了代码就改注释：过期注释比没有注释更危险，它会主动骗人

7.4 函数：小、单一、早返回

一个函数只做一件事。判断标准很土但有效：能不能用一句话说完它干了什么，而且这句话里不出现"然后"。"找到最大值然后打印然后写进文件"——三个动作，就该拆成三个函数。

嵌套三层 vs 早返回
// 不好读：括号越走越深，正常情况被埋在最里面
int getScore(Student *s) {
    if (s != NULL) {
        if (s->scores != NULL) {
            if (s->count > 0) {
                return s->scores[0];
            }
        }
    }
    return -1;
}

// 好读：先把所有异常挡在门口
int getScore(Student *s) {
    if (s == NULL) return -1;
    if (s->scores == NULL) return -1;
    if (s->count == 0) return -1;
    return s->scores[0];
}
  • 嵌套超过 3 层就该重构，早返回是最省事的解法
  • 函数控制在一屏内（约 50 行）。超了，说明它做的事不止一件
  • 参数超过 4~5 个，考虑打包成结构体
  • 有副作用的函数，名字里体现出来：list_pop 会改链表，list_peek 不会——看名字就该知道

7.5 写完先过一遍这六条

  1. 变量名读出来像人话吗？a1、a2、temp、flag 还剩几个？
  2. 缩进和大括号风格，整个文件是一致的吗？
  3. 有没有超过 3 层的嵌套？
  4. 有没有哪个函数超过一屏？
  5. 有没有注释在解释"这行在干什么"？如果有，多半是代码本身没写清楚
  6. 同一段逻辑复制粘贴了三处以上吗？那就该抽成函数了
风格之争没有标准答案
4 空格还是 2 空格、左括号换不换行、snake_case 还是 camelCase——这些争论了几十年也没结论。唯一真正重要的是：同一个项目里保持一致。想系统看规范，可以翻 Linux 内核的 Documentation/process/coding-style.rst 或 Google C++ Style Guide；但大一阶段，做到"你自己前后一致"就已经超过大多数人了。

08AI 使用原则：外功可以借，内功借不来

两年前的经验是"别依赖 AI，面试要手撕"。这句话现在只对了一半：手撕确实少了。越来越多的面试直接给你一个仓库、一个需求，让你开着 Copilot / Cursor 现场做，或者在 take-home 里随便用——考的是你和 AI 协作的能力：怎么拆问题、怎么审它的输出、跑不通了怎么定位。不适应这个变化，等于自己把机会推掉。

但另一件事没变：内功和外功，是两种能力。

  • 外功：工具用得熟、prompt 写得清楚、知道哪个模型擅长什么、能快速验收。速成很快——AI 自己就能教你，几周补得上来；但过时也快——去年的工具，今年已经没人提了
  • 内功：代码读得懂、对错判得出、内存画得出、崩了能定位、复杂度心里有数。这些 AI 教不了你，只能自己一行行写。学得慢，但不折旧——指针和内存模型几十年没变过

而面试考 AI coding 的时候，筛的恰恰是内功：AI 十秒钟给你二十行，你能不能一眼看出 i <= n 越界了、malloc 没判空、字符串字面量被改了——这才是他们想看的。AI 写得越快，这个判断力越值钱。

对比项内功外功
是什么读得懂、判得对、修得动会用工具、写得清 prompt、接得上流程
AI 能替你补吗不能能，几周就够
怎么练关掉 AI 手写、读别人的代码、自己 debug多用、多看别人怎么用
面试里怎么体现一眼看出 AI 的代码错在哪十分钟把能跑的原型搭起来
过时速度很慢，三十年前的书今天还能看很快，一年换一轮

把 AI 当副驾驶，别当代驾

  1. 自己先写 20 分钟，不是 0 分钟（那叫外包），也不是两小时（那叫浪费）
  2. 报错先自己读。要给 AI 看，就连"我试过什么、我猜是哪里"一起给它，别只贴一行错误
  3. 问"为什么"，别问"给我答案"。好问法："我这段在 n = 0 时输出乱码，为什么？"坏问法："这题怎么写"
  4. AI 给完先别运行：从头读一遍，标出你不同意的地方，再去验证
  5. 关掉对话自己重写一遍。写不出来，说明刚才只是"看懂了"，不是会了
  6. 自己补边界：0、1、最大值、空指针，AI 经常只写"正常情况"
四件别交给 AI 的事
① 替你读报错 ② 替你推指针和内存 ③ 替你交没跑过的代码 ④ 在你解释不了的时候替你提交。前三件是内功的练习机会，让出去就永远练不出来；第四件是事故。顺带一句：AI 写 C 也常错——gets()、sizeof 用错、指针类型对不上，它照样自信地给你。
一句话
外功让你快，内功让你不错；外功速成快，过时也快。去年大家用 Copilot，今年换 Cursor，明年不知道又是什么；而指针、内存、复杂度这些，三十年前的书翻开还是对的。工具会一轮轮换掉，判断力不会过期。AI 时代稀缺的不是"能写出代码"，是"能判断这段代码对不对"——前者越来越便宜，后者越来越贵。

09Debug 能力：比会写代码更重要

写代码的时间有一半是在调试。调试能力是初学者和入门者的分水岭。

第一原则

编译器的报错是朋友，不是敌人。报错列表先看第一条，后面的错误往往是连锁反应，改掉第一个可能全消失。编译时加上 -Wall -Wextra，让编译器把警告都说出来。

四个实用手段

  1. printf 大法：在最可疑的变量前后打印，缩小范围，初学者最实用
  2. 断点单步：VS Code + gdb 或 IDE 自带调试器，学会看变量值和调用栈。gdb 命令速查见 第 13 节
  3. 最小复现：把有问题的代码复制到新文件，删无关部分，一直删到 bug 消失，最后留下的那段就是问题
  4. 二分注释法：注释掉一半代码，看 bug 还在不在，不断二分定位

从对拍到 difftest：让两份实现互相验证

前面这些手段都靠"人眼看"。还有一种更省力的思路：写两份实现，让它们互相比。竞赛里叫对拍（也叫"拍"），工业界叫差分测试 differential testing，在模拟器和芯片领域简称 difftest。三个名字是同一个想法，差别只在于"比多细"。

对拍永远需要三样东西：

  • sol：你写的主程序，可能是错的（要验的就是它）
  • brute：暴力解法，慢得要死，但一定对
  • gen：随机数据生成器

然后循环：造一组数据 → 两个程序各跑一遍 → 比输出。一样就换下一组，不一样就立刻停下，把那组数据留下来。

三个程序都用 C 写，驱动用一段 shell 脚本（Windows 上在 Git Bash 里跑）：

run.sh
gcc -O2 -o sol sol.c
gcc -O2 -o brute brute.c
gcc -O2 -o gen gen.c

for i in $(seq 1 1000); do
  ./gen   > in.txt            # 造一组数据
  ./sol   < in.txt > a.txt    # 你的解
  ./brute < in.txt > b.txt    # 暴力解
  if ! diff -q a.txt b.txt > /dev/null; then
    echo "第 $i 组挂了，数据留在 in.txt"
    break
  fi
done

生成器是成败关键，几行就够，但要注意几点：

gen.c
#include <stdio.h>
#include <stdlib.h>

int main(void) {
    srand(1);                    // 固定种子：挂了能原样复现
    int n = rand() % 8;          // 规模小到暴力跑得完
    printf("%d\n", n);
    for (int i = 0; i < n; i++) printf("%d ", rand() % 10);
    return 0;
}
  • 规模小，但结构刁钻：n = 0、n = 1、全相同、已排序、逆序、全是极值——这些边界比随机数更容易拍出问题
  • 先用一道你确定写对的题验证脚本本身。如果连对解都报"不一致"，八成是输出末尾的空格或换行不一样，不是真 bug
  • 挂了之后先做最小化：把出错的输入不断删元素，删到"再删就不挂了"为止。最后往往只剩十几行，bug 一眼就能看出来

但注意：对拍比的是"最终输出"。而输出对了，过程可能是错的（越界写、未定义行为、内存泄漏）；更麻烦的是有些程序根本没有输出——比如你在写一个模拟器、一个操作系统。这时候就该 difftest 上场了。

difftest 把比较点从"最后一行输出"挪到"每执行一条指令之后的状态"：寄存器、PC、内存，逐字节比。参考实现一般是 QEMU 这类"已经确定正确"的权威实现。南京大学 PA 就是这么做的，伪代码简化后大概长这样：

difftest.c（简化）
void difftest_step(vaddr_t pc, vaddr_t npc) {
    CPU_state ref_r;

    ref_difftest_exec(1);                            // 让参考实现也执行一条
    ref_difftest_regcpy(&ref_r, DIFFTEST_TO_DUT);    // 取回它的寄存器

    if (!isa_difftest_checkregs(ref_r, pc)) {        // 逐字段比，不是整块 memcmp
        printf("[difftest] mismatch at pc = 0x%08x\n", pc);
        isa_reg_display();                           // 我的状态
        ref_reg_display();                           // 参考实现的状态
        assert(0);                                   // 当场停下
    }
}

报错大概长这样（不同 ISA 寄存器名不一样），差别就在那一个寄存器上：

运行输出

  dut:  eax = 0x00000000   ecx = 0x00000002

定位精度一组数据一条指令
代价要额外写一份暴力解要有金标准，慢很多，只在调试时开
本质是同一件事
找一个你信任的实现当标尺，用大量输入把你的实现和它对到完全一致。写编译器就对 clang，写 JSON 解析器就对 Python 的 json，写排序就对 qsort，写 NEMU 就对 QEMU。想不出反例、或者改一处怕弄坏另一处的时候，这套办法比盯着代码看有效得多。

还有两个坑，几乎人人踩过：

  • PATH：敲命令时系统只去 $PATH 列出的目录里找。用 echo $PATH 看一眼，自己装的东西不在里面就会出现 gcc: command not found
  • 引号：单引号 '...' 里面原样不动，双引号 "..." 会解析变量。变量用在路径上时永远加双引号，否则路径带空格会被拆成两个参数
  • 大小写敏感：Linux 下 Main.c 和 main.c 是两个文件

13.3 VS Code：日常写代码就住在这儿

13.4 gcc：编译不是一步完成的

很多人以为 gcc main.c 是一个动作，其实它内部走了四步。知道这四步，报错信息你就能看懂一半——因为报错会明确告诉你"死在哪个阶段"。

bash
gcc -E main.c -o main.i   # ① 预处理：展开 #include、#define，删掉注释
gcc -S main.i -o main.s   # ② 编译：C 代码变成汇编
gcc -c main.s -o main.o   # ③ 汇编：汇编变成机器码（目标文件）
gcc main.o -o main        # ④ 链接：拼上库，得到可执行文件

gcc main.c -o main        # 一步到位，等价于上面四步

预处理到底在干什么

上面写了 gcc -E，但这一步到底干了什么？一句话：它不懂 C 语法，只做文本替换。编译器还没开始理解你的代码，预处理先把源码"摊开"——所以预处理阶段连 int 是什么都不知道，更谈不上类型检查。

具体四件事：

  1. #include 是粘贴：把整个头文件的文本原样搬进来，遇到 #include 就递归展开。一个 <stdio.h> 展开后就有几千行
  2. #define 是替换：#define MAX 100 之后，代码里出现 MAX 的地方全部被换成了 100，纯粹的字符串替换，编译器根本不知道有个叫 MAX 的变量
  3. 条件编译是删代码：#ifdef / #ifndef / #endif 按条件整段保留或丢弃。同一份源码编出 Windows 版和 Linux 版，靠的就是这个
  4. 收尾：删掉所有注释、拼接反斜杠续行、插入 # 1 "main.c" 这样的行号标记——后面报错能指回你写的那一行，全靠这些标记

前后对比一下就清楚了：

main.c（你写的）
#include <stdio.h>
#define MAX 100

int main(void) {
    // 打印上限
    printf("%d\n", MAX);
    return 0;
}
预处理后（几万行，这里只截了最后一行）
int main(void) {

    printf("%d\n", 100);
    return 0;
}

注释没了，MAX 变成了 100，而 printf 的声明是从 stdio.h 里粘贴了一大堆东西换来的（上面那几千行里，绝大多数你根本用不到）。想亲眼看：

bash
gcc -E main.c -o main.i    # 只做预处理，得到展开后的文本
wc -l main.i               # 数数有多少行，通常几千到几万
tail -n 20 main.i          # 看最后几行，就是你的代码被替换后的样子
宏的坑：它真的只是替换
#define SQUARE(x) x*x，然后写 SQUARE(1 + 2)，你以为是 9，实际展开成 1 + 2*1 + 2，等于 5。正确写法是给每个参数和整体都加括号：#define SQUARE(x) ((x)*(x))。更推荐直接写 static inline int square(int x) { return x * x; }——有类型检查，也不会被重复求值。

还有一个必须知道的小事：#define MAX 100 后面不要加分号。因为它会被原样替换进代码里，int a[MAX]; 会变成 int a[100;];，直接语法错误。

为什么头文件一定要写 #ifndef

先看一个必然发生的场景。你有两个头文件，stack.h 用到了 list.h 里的节点定义，于是它自己 #include "list.h"；而 main.c 两个都要用：

main.c
#include "list.h"     // 直接包含
#include "stack.h"    // 这个里面又包含了一次 list.h

预处理是纯文本粘贴，它不认识"这个文件刚才是不是已经贴过了"。所以 list.h 的内容会被原样贴进 main.c 两次，展开后长这样：

预处理之后的 main.i（简化）
struct Node { int val; struct Node *next; };   // 第一次，来自 list.h
struct Node { int val; struct Node *next; };   // 第二次，来自 stack.h 里的 include
struct Stack { struct Node *top; };

同一个作用域里 struct Node 被定义了两次，编译器只能报错：

报错
In file included from stack.h:2,
                 from main.c:2:
list.h:1:8: error: redefinition of 'struct Node'
    1 | struct Node { int val; struct Node *next; };
      |        ^~~~

注意报错里的 In file included from stack.h:2, from main.c:2——它明确告诉你"这个文件是被谁带进来的"。头文件卫士就是专门堵这个洞的。

写法只有三行，但每一行都有作用：

list.h（加了卫哨）
#ifndef LIST_H          // 如果 LIST_H 这个宏还没被定义
#define LIST_H          // 那就定义它，然后继续往下读
                        // （反过来：已经定义过，就跳到最后的 #endif）
struct Node {
    int val;
    struct Node *next;
};

#endif /* LIST_H */

走一遍就明白了：

  • 第一次包含：LIST_H 还不存在 → #ifndef 成立 → 保留整段，同时 #define LIST_H 把它登记上
  • 第二次包含：LIST_H 已经定义 → #ifndef 不成立 → 整段被悄悄丢掉，一行都不剩

几个容易踩的点：

  • 宏名跟着文件名走：list.h → LIST_H，my_stack.h → MY_STACK_H。因为它是全局的宏，两个头文件撞名会互相把对方"卫士"掉，症状是"怎么少了一半声明"
  • #define 必须写在 #ifndef 里面，而且要紧紧跟在后面。写到外面去，就等于每次都登记一遍，等于没写
  • #endif 放在文件最后一行，后面加个 /* LIST_H */ 注释，几百行的头文件里才不会配错对
  • 它防的是"同一份源码里重复粘贴"，不是"被多个 .c 包含"。两个 .c 各自包含 list.h 是完全正常的，各自展开一份，互不影响
#pragma once 能不能用
能。第一行写 #pragma once，编译器自己记住"这个文件路径已经展开过"，不用你起名字，也不会撞名。它不是 C 标准的一部分，但 GCC / Clang / MSVC 全都支持，日常写作业用它更省事。唯一要小心的是同一个文件通过不同路径（软链接、多份拷贝）被包含时，它可能认不出来——而 #ifndef 只认宏名，反而更稳。两种都行，别在同一个文件里混着写。

参数不用背全，这些必须熟：

参数作用什么时候用
-o 名字指定输出文件名永远写，不写默认叫 a.out
-Wall -Wextra打开警告永远开，很多 bug 它提前告诉你
-g生成调试信息要调试就必须加，否则 gdb 看不到变量名和行号
-O0 / -O2优化级别调试用 -O0，交作业/跑数据用 -O2
-std=c11指定语言标准避免编译器默认标准不一致导致的怪问题
-c只编译不链接多文件工程分开编译时用
-I 目录加头文件搜索路径#include "my.h" 找不到时
-L 目录 -l库名加库路径与库用 math.h 要写 -lm
背下这一行，够用一整年
gcc -std=c11 -Wall -Wextra -g -O0 main.c -o main —— 编译期把警告全打开，调试信息带上，优化关掉。以后所有作业都从这里开始改。

C 和汇编怎么对应：一行语句变成哪几条指令

四阶段里第 ② 步「编译」就是把 C 变成汇编。这一步不必神秘化，它的规律很死：变量落到栈上的固定槽位，运算先进寄存器，分支变成比较加跳转，函数变成 call 和 ret。想亲眼看，把 -S 加进命令就行：

bash
gcc -S -O0 -masm=intel main.c -o main.s   # 只到汇编，Intel 语法（更好读）
cat main.s                                # 直接看

不加 -masm=intel 出来的是 AT&T 语法，两者说的是同一件事，只是写反了：

语法同一条 a = 42
AT&T（gcc 默认）movl $42, -4(%rbp)
Intelmov DWORD PTR [rbp-4], 42

区别就三条：AT&T 是源在前、目的在后，寄存器带 %，立即数带 $；Intel 全部反过来，更像人话。加 -masm=intel 之后，网上教程和教材里抄来的汇编才看得懂。

先认识几个寄存器，够看 90% 的代码：

寄存器干什么的
rax返回值、临时结果。低 32 位叫 eax，再低 16 位叫 ax
rdi rsi rdx rcx r8 r9整型参数按顺序放在这六个里，第 7 个起才走栈
rsp栈顶指针，push / pop 就是在动它
rbp栈帧基址。局部变量都在 [rbp-8]、[rbp-16] 这些位置
rip下一条要执行的指令地址，call / 跳转改的就是它

然后是这张对照表，左边是你写的，右边是编译器给的。看熟这张表，再看到汇编就不慌了：

C 代码对应的汇编（Intel 语法）要点
int a = 42;mov DWORD PTR [rbp-4], 42局部变量就是栈上一个固定槽位，名字编译完就没了
b = a + c;mov eax, [rbp-4]
add eax, [rbp-8]
mov [rbp-12], eax		运算必须先搬进寄存器，内存之间不能直接相加
if (a > b) ...cmp eax, [rbp-8]
jle .L2		条件是反着跳的：不满足就跳过 if 块
for (i = 0; i < n; i++).L2: cmp ... jge .L3
... ; jmp .L2		循环 = 标签 + 比较 + 条件跳走 + 末尾跳回
f(a, b);mov edi, a
mov esi, b
call f		实参先摆进 rdi/rsi，返回值回来时在 eax 里
p = &a;lea rax, [rbp-4]只算地址，不读那块内存——所以 & 和 [] 能被合并成一条
*p = 100;mov rax, [rbp-16]
mov DWORD PTR [rax], 100		两步：先把地址读进寄存器，再往那个地址写
return s;mov eax, [rbp-4]
leave / ret		返回值固定走 eax，ret 就是把 rip 弹回调用方

注意「DWORD PTR」这四个字：它标的是宽度。char 是 BYTE（1 字节）、short 是 WORD（2）、int 是 DWORD（4）、指针和 long 是 QWORD（8）。指针类型写错、printf 格式符用错，在汇编这一层看就是宽度对不上——它不会报错，只会读错几个字节。

拿一个真函数走一遍，比看表有用：

C
int sum(int *a, int n) {
    int s = 0;
    for (int i = 0; i < n; i++) {
        s += a[i];
    }
    return s;
}
对应的汇编（-O0，注释是我加的，省掉了几条地址计算）
sum:
    push    rbp                    ; 保存调用方的栈帧
    mov     rbp, rsp               ; 建立自己的栈帧
    mov     QWORD PTR [rbp-24], rdi   ; 参数 a（指针，8 字节）存进栈
    mov     DWORD PTR [rbp-12], esi   ; 参数 n（int，4 字节）存进栈
    mov     DWORD PTR [rbp-4], 0      ; s = 0
    mov     DWORD PTR [rbp-8], 0      ; i = 0
.L2:                               ; ← 循环开头
    mov     eax, DWORD PTR [rbp-8]    ; 取 i
    cmp     eax, DWORD PTR [rbp-12]   ; 和 n 比
    jge     .L3                       ; i >= n 就跳出（反着跳）
    mov     eax, DWORD PTR [rbp-8]    ; 取 i
    cdqe                              ; 32 位扩成 64 位（做地址要用）
    lea     rdx, [rax*4]              ; i * sizeof(int) = i * 4
    mov     rax, QWORD PTR [rbp-24]   ; 取 a 的地址
    add     rax, rdx                  ; a + i*4 → 第 i 个元素的地址
    mov     eax, DWORD PTR [rax]      ; 顺着地址读出 a[i]
    add     DWORD PTR [rbp-4], eax    ; s += a[i]
    add     DWORD PTR [rbp-8], 1      ; i++
    jmp     .L2                       ; 跳回循环开头
.L3:
    mov     eax, DWORD PTR [rbp-4]    ; 返回值放 eax
    pop     rbp                       ; 恢复调用方的栈帧
    ret

这段汇编把前面几节讲的东西全兑现了：

  • 局部变量真的是"栈上的槽位"：s 在 [rbp-4]、i 在 [rbp-8]，编译器排的位置，跟你写的顺序没关系
  • a[i] 被拆成"基址 + i×4"：lea rdx,[rax*4] 算出偏移，再 add 到指针上。这就是 5.5 节说的"指针算术按类型步进"的物理实现
  • 函数返回后栈帧就作废了：pop rbp 之后 [rbp-4] 那块内存不再属于你。所以"返回局部变量的地址"是 UB——不是玄学，是这块地已经被回收了
  • 每次递归调用都会 push 一层新栈帧：递归太深撑爆栈 → 段错误，原因也在这里
别拿 -O2 的汇编逐行对源码
-O0 是"一条语句一条语句地翻"，最适合学习。-O2 会把变量全塞进寄存器、把循环改成指针步进、把整段计算提出来甚至向量化——你写的第 5 行可能跑到第 20 行去执行，也可能整段消失。要对照语法就看 -O0；要研究优化，就换个心态，别指望一一对应。顺便说，这也是"UB 在 -O2 下行为突变"的原因：优化器正是按"你保证过不会越界"来重排代码的。

要不要背？不用。只要能把骨架对上：变量 → 栈槽位、表达式 → 寄存器、if/for → 比较加跳转、函数 → call 加 ret。真需要看汇编的场合就三个：调段错误要看寄存器、ICS 的 Bomb Lab 要读反汇编、想搞明白某个 UB 到底怎么被优化掉。其余时候，知道它长什么样就够了。

报错也分两类，区别很重要：

  • 编译错误：语法、类型不匹配。编译器能指出具体行号，按第一条改
  • 链接错误：undefined reference to 'foo'。函数声明了但没定义，或者编译时忘了把实现它的 .c 加进去、忘了 -lm。这类错误没有行号，新手最容易懵
  • 运行时崩溃（段错误）：编译链接都过了，一跑就死。这已经不归 gcc 管了，交给下面这个工具

13.5 多文件：为什么要分 .h 和 .c，路径又是怎么找的

单文件写到几百行以后会同时遇到三个问题：找不到函数、改一行要重编全部、两个人没法同时改。解决办法就是拆文件。但拆之前得先分清两个词：

  • 声明（declaration）：告诉编译器"有这么个东西，它长这样"。函数原型、struct 定义、extern 变量都算
  • 定义（definition）：告诉编译器"它到底是什么"，真正分配内存、给出函数体

规则只有一条：定义只能有一份，声明可以有很多份。而编译器是单个 .c 单独编译的——它编 main.c 时根本看不见 list.c。所以 main.c 想调用 list_push，就必须先看到它的声明，这就轮到头文件了。

于是分工固定成这样：

文件放什么不放什么
list.h函数原型、struct / typedef、宏、extern 变量声明函数体、变量定义（否则每个包含它的 .c 都会各定义一份）
list.c函数的定义、私有变量、static 辅助函数不需要暴露给别人的东西
main.cmain 函数，调用别人的接口别人的实现细节

一个最小可跑的三件套：

list.h（接口）
#ifndef LIST_H
#define LIST_H

struct Node {
    int val;
    struct Node *next;
};

void list_push(struct Node **head, int val);
int  list_sum(const struct Node *head);

extern int g_node_count;   // 声明：只是个"通知"，不分配内存

#endif /* LIST_H */
list.c（实现）
#include "list.h"

int g_node_count = 0;      // 定义：真正在这里分配

void list_push(struct Node **head, int val) {
    struct Node *n = malloc(sizeof *n);
    if (!n) return;
    n->val = val;
    n->next = *head;
    *head = n;
    g_node_count++;
}
main.c（调用方）
#include "list.h"

int main(void) {
    struct Node *head = NULL;
    list_push(&head, 1);
    return 0;
}

注意到 list.c 自己也 #include "list.h" 了吗？这不是多余——让编译器替你检查声明和定义是否一致。参数写错了，编译就会报错，比链接期或运行期才发现强得多。

编译命令：一步和分步

bash
# 一步到位：把所有 .c 都列上
gcc -std=c11 -Wall -Wextra -g main.c list.c -o app

# 分步：更接近真实工程的做法
gcc -c -std=c11 -Wall -Wextra -g main.c -o main.o
gcc -c -std=c11 -Wall -Wextra -g list.c -o list.o
gcc main.o list.o -o app

分步的价值在于：改了 list.c 就只重编 list.c，main.o 原样复用。文件多了以后，这个差别是几十秒和几秒的差别。-c 的意思是"只编译成 .o，先别链接"——链接是最后一步，把各个 .o 里的符号拼起来。

文件路径到底怎么找

这是多文件最容易懵的地方，因为编译器没有"项目根目录"这个概念，它只认两样：你在命令行里写的路径（相对你当前所在的目录），以及 -I 参数给的目录。IDE 之所以看起来"什么都能找到"，是它在背后替你补了这些参数。

一个正常的项目长这样：

目录结构
project/
|-- include/
|   `-- list.h
|-- src/
|   |-- main.c
|   `-- list.c
`-- build/

在 project/ 目录下敲：

bash
gcc -std=c11 -Wall -Wextra -g -Iinclude src/main.c src/list.c -o build/app

拆开看每个路径归谁管：

写法谁用它相对谁
src/main.cgcc 直接读这个源文件你敲命令时所在的目录
-Iinclude只影响 #include 的搜索同样是当前目录
-o build/app输出文件放哪当前目录；build/ 必须已经存在，gcc 不会帮你建目录
#include "list.h"预处理阶段找头文件先找包含它的那个文件所在目录，再找 -I，最后系统目录
<stdio.h>同上只找 -I 和系统目录，不找你自己的目录

几条由此推出的结论，都是踩过才记住的：

  • 双引号和尖括号的区别就在第一站。"list.h" 先在自己身边找（src/main.c 里写它，先看 src/list.h），所以同一目录的头文件不用加任何参数；<stdio.h> 跳过这一步，直接去系统目录，这样才不会误撞上你自己写的同名文件
  • -I 只管头文件，不管 .c。写了 -Iinclude 之后，#include "list.h" 能找到 include/list.h，但 list.c 还是得自己写全路径 src/list.c
  • 头文件里再 #include，是相对那个头文件的目录算的，不是相对 main.c。所以 include/ 下的头文件互相引用，写文件名就行
  • 报错 fatal error: list.h: No such file or directory，八成是 -I 写错或没写；报错 No such file or directory 指向 main.c 本身，那是你站错目录了，先 pwd 看看自己在哪
  • Windows 上别用反斜杠。gcc src\main.c 在 shell 里 \ 是转义符，会变成奇怪的字符；统一写正斜杠 src/main.c，MinGW 一样认
  • 别在命令里写死绝对路径。E:/Desktop/project/src/main.c 换台机器就废，而且复制到别人电脑上第一条命令就跑不起来

多文件之后，编译命令会越来越长，所以最终还是要交给 Makefile——但这次你知道它在替你做什么了（$< 是源文件，$@ 是目标文件，-I 和路径原样抄进去）：

最小可用的 Makefile（注意命令前面是 Tab，不是空格）：

Makefile
CC     = gcc
CFLAGS = -std=c11 -Wall -Wextra -g -Iinclude

app: src/main.c src/list.c include/list.h
	$(CC) $(CFLAGS) src/main.c src/list.c -o build/app

clean:
	rm -f build/app

之后只要敲 make 就能编译，make clean 清理。以后加文件，把新的 .c 和 .h 加到 app: 后面那行依赖里就行。

13.6 gdb：程序崩了，别再靠 printf 猜

printf 能定位问题，但它只能告诉你"我打到这一行了"。gdb 能告诉你崩溃时完整调用栈、每一层的变量值、内存里到底是什么。段错误、越界、野指针这几类问题，printf 基本查不出来。

前提：编译时必须加 -g，否则 gdb 只能看到地址。

命令缩写作用
runr从头开始跑
break main / break list.c:12b下断点，按函数名或行号
nextn单步执行，不进入函数
steps单步执行，进入函数
continuec放行到下一个断点
print p / print *pp看变量值 / 看指针指向的内容
backtracebt看调用栈，崩溃排查第一命令
frame 1f 1切到栈的第 1 层，看调用者的变量
info locals一次列出当前所有局部变量
x/4xw p按十六进制看 p 指向的 4 个字内存
quitq退出

一次真实的排错长这样（链表写错了导致段错误）：

gdb 会话
$ gcc -g main.c -o main
$ gdb ./main
(gdb) run
Program received signal SIGSEGV, Segmentation fault.
0x0000000000401156 in node_value (p=0x0) at list.c:12
12          return p->value;
(gdb) bt
#0  node_value (p=0x0) at list.c:12
#1  0x0000000000401180 in main () at list.c:30
(gdb) frame 1
(gdb) print head
$1 = (struct Node *) 0x0
(gdb) quit

读法：程序死在 list.c 第 12 行，p 是空指针。bt 显示是 main 调的，切到第 1 层一看 head 本来就是 NULL——问题不在 node_value，而在 main 里没有判空。这就是 gdb 比 printf 值钱的地方：它直接告诉你"错在谁身上"。

三个提高效率的技巧：

  • gdb -tui ./main 或运行中按 Ctrl+X 再按 A，切出源码窗口，边看代码边走
  • print arr@5 直接打印数组前 5 个元素，print/x var 用十六进制显示
  • watch x：变量 x 一被修改就停下来，专治"不知道谁把它改坏了"

13.7 git：不是可选项

git 最容易被误解成"给别人协作用的"。其实对单人项目它更值钱：写崩了能回滚，改错了能对比，交作业有记录。而且 GitHub 主页现在基本等于程序员的第二张简历。

bash
git init                          # 把一个文件夹变成仓库
git status                        # 最常用：哪些改了、哪些已暂存
git add list.c                    # 把指定文件放进暂存区
git commit -m "实现链表插入"       # 存一个快照，说明写"做了什么"
git log --oneline                 # 看历史，一行一条
git diff                          # 看还没 add 的具体改动

分支和远程，四个命令就够开始：

bash
git switch -c dev                  # 新建并切到 dev 分支（老写法 checkout -b）
git switch main                    # 切回 main
git merge dev                      # 把 dev 合进来
git push -u origin main            # 第一次推，之后直接 git push

真正救命的是下面这几条，建议抄在便签上：

我把什么搞坏了怎么救
某个文件改乱了，想丢弃改动git restore main.c
已经 add 了，但不想提交它git restore --staged main.c
提交信息写错（还没 push）git commit --amend
手头没做完，但要临时切分支git stash → 回来 git stash pop
刚提交的内容想撤掉（保留代码）git reset --soft HEAD~1
分支删错了、reset 过头了git reflog 找回历史位置，几乎万能

另外：别把编译产物提交进去。仓库根目录放一个 .gitignore：

.gitignore
*.o
*.exe
a.out
.vscode/
build/
这四样怎么练
不需要先系统学完再动手。做法是：给自己定一周"只用命令行" —— 用 gcc 代替 IDE 的编译按钮，用 gdb 代替 printf，每次改完代码就 git add + commit。一周之后这些就变成肌肉记忆了。真卡住了，回 Missing Semester 的第 1、2、6 讲对着补。
